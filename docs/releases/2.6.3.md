# Mynah 2.6.3

The glasses stopped being refused, and started reading like a conversation.

## The message that named the wrong machine

The report was exact and it did not sound like a bug in the link: *the first
question works, the second says "Your Mac's Mynah refused this recording.
Update Mynah on the Mac, restart it…"*, on a pairing that had not changed, from a
Mac that had already been updated and restarted.

Every part of that sentence is a fingerprint. Mynah's companion produces it in
exactly one situation: the endpoint answered `unknown control`, which an endpoint
can only do when it does not understand the command it was sent — and that
command has existed since 2.5.1. So the **process answering the glasses was from
an older build than the daemon running on the Mac.**

The mechanism is one line of ordinary carelessness, in the place where it costs
the most. The token in a pairing is written down and reused, so the endpoint that
serves it is started again with the *same* token after every restart — and
nothing in the relay's registration is exclusive. An endpoint that survived a
crash, a force quit, or an update landing on a running daemon therefore keeps
polling for the same link as the endpoint that replaces it, and the relay hands
each offer to whichever of the two happens to be waiting. They race. The owner
sees one question answered and the next one refused, by a build that is not the
one they are running, with nothing wrong anywhere they can look. Restarting Mynah
did not help because the leftover was not the new daemon's child.

Two rules close it, and they are the two halves of one thing:

* **Before its first poll, an endpoint stops any other process serving its own
  token** — matched on the token *and* the kind, so a spoken call is never
  mistaken for the glasses pairing. That cures a leftover that already exists,
  including one from a build too old to know about any of this.
* **The endpoint now exits with the daemon that started it** (`-exit-with-parent`),
  so crashes, force quits and updates stop creating leftovers in the first place.

The same reading of the same evidence turned up a second, smaller way to get
"the second question is refused": a recording that arrived with under 400 ms of
audio returned its error and *left the capture state recording*, so every later
question on that connection was refused until the companion reconnected. The
state is now cleared before the error is returned, and a stray stop is a no-op.

## The companion says what actually happened

While chasing that, one more thing was wrong in a way that made the chase
longer. Every refusal from the relay arrived at the phone as the same sentence —
*"Mynah is offline or the pairing was revoked"* — including the three refusals
that have three different next steps. A link that has genuinely expired now says
so and says to send `//g2` for a new one; a Mac that is not holding a poll yet
says that; a Mac that took too long asks for another tap; and a phone that cannot
reach the relay blames the phone. None of them claims the pairing is revoked, and
none of them repeats a DOMException's internal text.

## A conversation reads as a conversation

Reported from the glasses: *"there is no way to add a follow-up question… and it's
broken up into cards instead of one long thread."* Both halves were true, and the
first was the more interesting one: tapping a finished answer has always
continued that conversation and threaded its context on the Mac, but nothing on
the glasses said so — so a follow-up looked exactly like a first question.

Companion **0.2.9**:

* Opening any turn shows **the whole conversation, oldest turn first**, so a
  follow-up no longer hides the question it answered.
* The last page of a finished answer ends with **"Tap to follow up."**, and the
  recording that follows announces itself as **"Follow-up…"** while it is open.
* Where the asks are listed, a continuation is marked **↳**, and a follow-up
  joins its thread locally the moment it is sent rather than flickering as a
  separate conversation until the Mac's snapshot arrives.
* Each New ask still starts its own conversation with its own context.

## The display goes to sleep

The dashboard used to stay lit indefinitely. Twelve seconds after the last thing
that changed, every text container goes to the firmware's brightness 0 and the
four image containers — clock digits, title, battery, weather icon — are sent
empty bitmaps of their own shape, because an image carries pixels and no
brightness at all. A tap, a swipe or an arriving answer lights it again, and a
recording is never slept through. Deliberately not `shutDownPageContainer`: a
page that is still up still receives taps, so waking costs a rebuild rather than
a trip back through Even's app list.

That is also the only notification this companion can give, and the release
notes say so rather than implying otherwise. The pinned Even SDK has no
notification entry point and no way to reach Even's mirrored phone
notifications, so a finished answer is announced by the display — which is
exactly why the sleep had to be the thing that lights back up.

## The bundled brain

**SAGE stays at 11.19.22**, which is the newest published release at the moment
of this cut and the same node 2.6.2 shipped. Nothing in this release touches the
tool surface, so there is no allowlist question to re-answer and no reason to
move a pin that was set yesterday and re-vendored with it.

## Validation

2,569 Mac tests executed with zero failures, 21 skipped on this checkout (17 with
the live-node tests staged, which is how the release path runs them). The
companion's 60 tests pass, and so does the whole Go `webrtc` suite — including
two new tests that walk two recordings over one real data channel, and the
sibling-reaping and parent-watch tests. The Mac app is Developer ID signed,
Apple notarized and stapled.

Download the DMG for Mac installation, and install the companion package from the
Even Hub section of the site for developer installation.
